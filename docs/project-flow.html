03真实分析内部：三个 Task 与 Agent 循环

AnalysisWorkflow.run() 把上一个 Task 的返回值作为下一个的入参，任一步抛异常就 break 并返回错误字典。

顺序文件 / 函数做什么返回值
1 app/workflow/tasks.py:10
discovery_task		 find_target_asin() 确定目标 ASIN，预热目标商品评论采集，run_discovery() 找候选竞品，取前 3 个 原 data 字典，追加 target_asin 与
competitors=[{name, asin, url}]
2 app/workflow/tasks.py:54
analysis_task		 3 线程并发调用 competitor_agent() 逐个竞品分析，单个失败不影响其余 {task_id, target_product, analyses:[{competitor_name, competitor_asin, competitor_url, analysis}]}
3 app/workflow/tasks.py:121
report_task		 generate_markdown() 拼报告，save_report() 写入 reports/ Path("reports/<task_id>.md")

competitor_agent()（app/agent/agent.py:70）是一个最多 3 轮的 function-calling 循环：

search_knowledge

本地 RAG 检索，向量存在 app/data/vector_store.json。返回 {query, results:[{text, source, score}]}。

search_web

Tavily 搜索 + 网页正文读取 + extract_product() 结构化。返回 ProductExtraction（product / price / features / source / rating / reviews / bullet_points）。

analyze_product_reviews

BrightData 抓评论后交给评论分析流水线，返回 ReviewAnalysis 字典（痛点、优点、改进建议、总结）。

最终输出

模型输出 JSON → 校验成 CompetitorAnalysis（目标产品、竞品、价差、总结）；失败返回 {error, message}。

最后一轮会追加一条 system 消息并设置 tool_choice="none"，强制模型直接输出 JSON，避免无限调用工具。

05Docker 与 MySQL 如何连接

Docker 只负责 Worker 和 Redis；MySQL 是宿主机上的 Windows 服务，容器通过 host.docker.internal 反向访问它。

当前运行中的容器

容器镜像端口作用
agent-workeranalysissystem-worker—RQ Worker，真正的分析进程
agent-redisredis:7-alpine127.0.0.1:6379任务队列
neo4jneo4j:57474 / 7687与本项目无关

MySQL 不在容器里：Windows 服务 MySQL80，监听 0.0.0.0:3306。

compose.yaml 逐项含义

services:
  worker:
    build:
      context: .
      dockerfile: docker/worker.Dockerfile

    working_dir: /workspace
    volumes:
      - .:/workspace          # 整个项目挂进容器，reports/ 与宿主机共享

    env_file:
      - .env                  # 复用本机配置

    environment:
      REDIS_URL: redis://agent-redis:6379/0   # 覆盖：容器内用服务名，不能用 127.0.0.1
      DB_HOST: host.docker.internal           # 覆盖：访问宿主机 MySQL 的固定域名
      MOCK_MODE: "false"                      # 容器内跑真实 Agent，不是 mock

    networks:
      - agent-network         # external: true，需提前创建

networks:
  agent-network:
    external: true
为什么必须覆盖：.env 里写的是 DB_HOST=127.0.0.1，那是给本机 FastAPI 用的。同一个文件被容器读进去后，127.0.0.1 指向容器自己，所以 compose.yaml 用 environment 把它改成 host.docker.internal；Redis 同理改成服务名 agent-redis。

MySQL 连接代码

backend/app/db/database.py 是唯一入口：

  • parents[3] 定位项目根，load_dotenv() 读取根目录 .env
  • 读取 DB_HOST / DB_PORT / DB_USER / DB_PASSWORD / DB_NAME，缺密码直接 RuntimeError
  • 用 URL.create(drivername="mysql+pymysql", ...) 构建连接串，charset=utf8mb4（URL 对象而非字符串拼接，密码含特殊字符也不会出错）
  • create_engine(pool_pre_ping=True, pool_recycle=1800)：防止 MySQL 空闲断连
  • SessionLocal 会话工厂 + Base ORM 基类 + get_db() 依赖

实际写库用的是 services/*.py 里的 with SessionLocal() as db:。get_db() 虽然定义了，但路由层目前没有使用。

建表方式

项目里没有迁移脚本，Base.metadata.create_all() 只出现在 tests/testDb/test_db_models.py。当前库 competitor_analysis 中有 4 张表：

表是否在用说明
projects使用中task_id 主键，status / result / error
reports使用中task_id 外键且唯一，存 Markdown 正文与文件路径
products未写入CRUD 已写，但没有任何调用方
sources未写入同上，属于预留

正确的启动顺序

# 1. MySQL（Windows 服务，通常已自启）
net start MySQL80

# 2. Redis 容器与网络（只需一次）
docker network create agent-network
docker run -d --name agent-redis --network agent-network \
  -p 127.0.0.1:6379:6379 redis:7-alpine

# 3. Worker（在项目根目录）
docker compose up -d --build worker

# 4. FastAPI（backend 与 app 两个包都要可导入，必须在项目根执行）
uvicorn backend.app.main:app --reload --port 8000

# 5. 前端
cd frontend && npm run dev

06容易踩的点

MOCK_MODE 决定真假分析

本机直接跑 FastAPI 时默认 true，只会生成假报告；只有容器里被覆盖成 false。本机单跑后端不出真报告是正常现象。

报告是双写的

接口读的是 reports.markdown，reports/*.md 只是备份。手动改 md 文件不会同步到接口。

任务超时 1800 秒

队列默认超时与 job_timeout 都是 30 分钟；一轮真实分析（搜索 + 抓取 + 3 轮 LLM）容易逼近这个上限。

host.docker.internal 的适用范围

只在 Docker Desktop 上有效。换成 WSL2 原生 Docker 或 Linux 主机时需要另行配置。

被轮询接口的 404 分支

任务不存在返回 404；任务完成但报告缺失也返回 404，前端会把两种情况都当成失败提示。

孤儿 pending 任务

入队成功但 Worker 未消费时会长期停在 pending，不会自动超时；需要手动清理或重投。

接口鉴权与 CORS

/api 下的路由统一要求请求头 X-API-Key，值取自根目录 .env 的 API_KEY；前端用 frontend/.env 的 VITE_API_KEY 携带。跨域只放行 ALLOWED_ORIGINS 白名单，/health 不鉴权。
